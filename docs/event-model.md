# 事件与计数

按键怎么成组、计数怎么算。这是整个插件最容易出错的地方，改动前请先读。

## 键的身份

一个键由它的**显示标签**标识，不是调用方传进来时的拼写。

```js
const keyId = raw => config.displayLabel ? config.displayLabel(raw) : raw;
```

`press()` 里所有比较都过 `keyId`，因为键盘路径喂的是原始 evdev 码（`KEY_LEFTCTRL`），
鼠标、滚轮、IPC 预览喂的是标签（`Ctrl`）。不统一的话，同一个物理键会在
`heldKeys` 里存成两种写法，重按时匹配不到自己的键帽，旁边多出一个重复键帽。

副作用：**左右 Ctrl 都映射成 `Ctrl`**，所以左右交替按被视为同一个键的重复，
不会各自计数。这是有意的——第二个按下时状态机按 autorepeat 吞掉。

## 行（group）

一次手势的所有键在一行里。行有 uid，渲染层靠它决定是复用还是重建——
uid 变了整个 delegate 会被拆掉重建，视觉上就是角标闪烁，所以能原地递增就别换 uid。

松开的行内成员**不会立刻删除**，会逗留（linger）到行内某个键被重按。
这是 `Ctrl+C+V` 能读成一行的原因：用户松开 C 是为了去够 V，不是要重新开始。

## 计数语义

**count = 这个键被按下的次数，永不回退。**

| 操作 | 结果 |
| --- | --- |
| 连按 4 次 Ctrl，再按 Ctrl+C | `Ctrl×5+C×1` |
| Ctrl+C 重打一次 | `Ctrl×2+C×2` |
| Ctrl+C 之后按 Ctrl+V | `Ctrl×2+V×1` |
| 按住 Ctrl 不放 | 计数不涨（autorepeat 在内核层就被丢了） |

历史上这里修反过一次：曾经在和弦形成时把修饰键落回 1，理由是"新组合重新计数"。
从界面上看那和"计数自己重置了"无法区分，而这正是用户最早报的抱怨。

## 暂定修饰键（pending）

单独按下一个修饰键时，这一个事件**物理上无法自证**它是：

- 连敲 Ctrl 的第 N 次，还是
- `Ctrl+C` 的第一个键

所以它是**暂定**的：照常画出来（孤立的键帽总得显示点什么，count = `settled + 1`），
由下一个事件裁决。

**release 不能裁决。** 松开一个孤立的修饰键，无论它是敲完了还是组合才打一半，
看起来一模一样。这个悬念必须活过松键。

下一个按下到来时分三种情况：

| 下一个键 | 判定 | 结果 |
| --- | --- | --- |
| 还是这个键 | `resumed` | 连敲继续，`settled + 1` |
| 属于被中断那一行 | `retyped` | 重打：撤销暂定行，整行各 +1 |
| 其他键，且暂定键**仍按住** | `resolves` | 新和弦：修饰键保留 `settled + 1`，未按住的旧成员丢弃 |
| 其他键，暂定键**已松开** | 不成立 | 下一个键按自己的规则独立判定（详见[过滤与热键](filtering.md)） |

最后一行是关键：`Ctrl` 按下 → 松开 → 按 `R`，不能拼成 `Ctrl+R`。
暂定状态虽然活过松键，但一旦那个键已经不在手上，就不再替下一个键说话。

## 与上游的差异

上游 `key_event.ts` 的处理：

- `onKeyPress` 里，最后一组超过一个键时直接 `new KeyEvent(...)` 建新组，
  计数从 1 开始 → 组合键在手时计数永远到不了用户眼前。这里改成**原地递增**，
  uid 和计数都活下来。
- `ignoreEvent` 只看 `pressedKeys[0]`（第一个按住的键）。两键同时按下时谁先到是竞态，
  同一个手势会时显示时不显示。这里改成"序列里任一键命中"，见[过滤与热键](filtering.md)。

两处都是有意的偏离，各自都有测试锁住。
